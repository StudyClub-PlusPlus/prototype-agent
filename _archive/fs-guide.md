# 기능정의서(FS) 작성 가이드 (웹 구축)

> FS = **기능 도메인 단위 영속 명세**. Function 들의 묶음이며 `fs/{fs-slug}/FS.md` 하나가 SoT.
> Epic·Story 가 전달 단위(일시적)라면 FS 는 시스템이 계속 유지하는 정의다.

## 0. Function 이란

**시스템이 해야 하는 구현 요건 1단위.** 사용자 관점 요구(Story)와 구분한다.

| | Story | Function |
|---|---|---|
| 관점 | 사용자 | 시스템 |
| 문장 | `[Actor]로서, ~할 수 있다.` | `~을 처리한다 / ~을 보장한다` |
| 예 | 운영자로서, 스터디를 등록할 수 있다. | 스터디 레코드를 생성·저장한다 |

- **Story ↔ Function = N:N.** 하나의 Function 이 여러 Story 를 Blocks 할 수 있다(공유 기능 재사용)
- 기획 수준이되 **기술자가 읽고 구현할 수 있는 정도**까지 쓴다. 구체 코드·아키텍처 선택은 FS 범위 밖

## 1. FS 문서 구조

```markdown
---
fs_slug: study-catalog
title: 스터디 카탈로그
module: 콘텐츠
---

# 스터디 카탈로그 FS

## 1. 범위
이 도메인이 책임지는 것 / 책임지지 않는 것.

## 2. 데이터 정의
| 엔티티 | 필드 | 타입 | 필수 | 제약 | 비고 |
|---|---|---|---|---|---|
| Study | title | string | ✅ | 1~60자 | 목록 카드 24자 권장 |
| Study | deadline | date | | | 없으면 마감 없이 모집 |

- **상태 값**과 전이 규칙을 명시 (어떤 조건에서 어떤 상태가 되는가)
- 파생값(계산으로 나오는 값)은 **저장하지 않고 계산식**을 적는다

## 3. Functions
### FN-007 스터디 등록 처리
- **동작**: 입력 검증 → 레코드 생성 → 목록 캐시 무효화
- **입력/출력 계약**: 요청 필드, 응답 형태, 오류 코드
- **실패 처리**: 검증 실패 / 중복 / 저장 실패 각각의 응답과 사용자 노출 문구
- **완료 정의**: 무엇이 되면 이 Function 이 끝난 것인가
- **Blocks**: ST-012, ST-019

## 4. 외부 연동 (SYS-02)
| 대상 | 용도 | 실패 시 | 비고 |
|---|---|---|---|
| OAuth 공급자 | 로그인 | 로그인 화면에 오류 표시, 재시도 유도 | 토큰 저장 위치 명시 |

- 외부 시스템은 **사용자 스토리 주체가 아니다.** 여기서 연동으로만 정의
- 벤더명은 소스에 명시된 경우에만. 아니면 일반명

## 5. 권한
| 동작 | 허용 Actor | 검증 위치 |
|---|---|---|
| 스터디 등록 | 운영자·관리자 | 서버 (클라이언트 가드는 보조) |

> **클라이언트 가드만으로 권한을 처리하지 않는다.** 화면을 숨기는 것은 UX이지 보안이 아니다.

## 6. 비기능 요건 (NFR)
해당하는 것만 구체 수치로. 근거 없는 수치 금지.
| 항목 | 기준 | 측정 방법 |
|---|---|---|
| 목록 첫 렌더 | LCP 2.5s 이하 (중간 사양·4G) | Lighthouse |
| 접근성 | 대비 4.5:1 이상, 키보드 전 조작 | 자동 검사 + 수동 |

## 7. 마이그레이션·호환
기존 데이터가 있으면 어떻게 옮기는지. 없으면 "해당 없음".
```

## 2. 웹 도메인 표준 (반드시 검토)

FS 작성 시 아래를 각 Function 에 대해 훑고, 해당 없으면 "해당 없음"이라고 명시한다. **침묵은 누락과 구분되지 않는다.**

### 2.1 상태·오류
- 로딩 / 빈 결과 / 부분 실패 / 전체 실패 각각의 화면과 문구
- 재시도 가능 여부와 방법
- 낙관적 업데이트를 쓰면 롤백 규칙

### 2.2 입력·검증
- 클라이언트 검증 = UX, **서버 검증 = 진실**. 둘 다 정의
- 경계값(최소·최대·빈 문자열·공백만)
- 중복 제출 방지(더블 클릭·네트워크 재시도)

### 2.3 URL·라우팅
- 목록 필터·탭·검색어를 URL 에 반영하는가 (공유·뒤로가기)
- 딥링크 진입 시 초기 상태

### 2.4 접근성
- 키보드만으로 전 기능 조작 가능한가
- 포커스 이동·가둠(모달), 스크린리더 라벨
- 색만으로 정보를 전달하지 않는가

### 2.5 성능
- 목록 크기 상한과 페이지네이션 방식
- 이미지 최적화·지연 로딩

### 2.6 국제화
- 문구를 하드코딩하지 않는가
- 날짜·숫자 형식, 언어별 레이아웃 깨짐

### 2.7 보안·개인정보
- 개인정보 수집 항목과 보관 기간
- 서버 권한 검증 위치
- 로그에 민감정보가 남지 않는가

### 2.8 프로토타입 갱신 대응 (§2.2)
프로토타입 새 버전이 들어오면 화면 차이(added/changed/removed)를 도출해 영향 Function 을 갱신한다. removed 화면에 걸린 Function 은 **자동 폐기하지 않고** 변경 계획에 올려 승인받는다.

## 3. 자가 검증 체크리스트

- [ ] 각 Function 에 입력/출력 계약과 실패 처리가 있는가
- [ ] 각 Function 이 최소 1개 Story 를 Blocks 하는가 (고아 Function 0건)
- [ ] 여러 Story 가 같은 기능에 의존하는데 Function 을 중복 만들지 않았는가
- [ ] §2 표준 8항목을 모두 훑고 해당 없음까지 명시했는가
- [ ] 권한 검증이 서버에 있는가
- [ ] NFR 수치에 측정 방법이 붙어 있는가
- [ ] 데이터 정의의 상태 전이가 빠짐없이 그려지는가
