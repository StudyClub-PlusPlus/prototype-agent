# 사용자 시나리오(US) 작성 가이드 (웹 구축)

> US 는 Story 를 **사용 흐름으로 합성**한 문서다. 새 요구를 만들지 않는다 — 레지스트리의 합성물.
> 위치: 횡단 시나리오 `_scenarios/US-{시나리오명}.md`.

## 1. 무엇을 쓰는가

한 사람이 목적을 달성하기까지의 **연속된 경로**. 화면 단위가 아니라 여정 단위다.

- 좋은 예: `US-스터디-찾아-신청하기` (방문 → 목록 → 상세 → 신청 → 확인)
- 나쁜 예: `US-스터디목록화면` (그건 화면 스펙이지 시나리오가 아니다)

## 2. 문서 구조

```markdown
---
scenario: 스터디 찾아 신청하기
actor: 회원
stories: [ST-003, ST-007, ST-012]
---

# 스터디 찾아 신청하기

## 전제
- 로그인 상태 / 비로그인 상태 등 시작 조건
- 필요한 데이터 상태 (모집중 스터디가 1건 이상 존재 등)

## 주 흐름
| # | 행동 | 시스템 반응 | 검증 포인트 (AC) |
|---|---|---|---|
| 1 | 스터디 목록에 진입 | 모집중 탭이 기본 선택되고 N건 노출 | AC-3 |
| 2 | 카드를 누른다 | 상세 화면으로 이동 | |
| 3 | 신청하기를 누른다 | 신청 화면 진입 | AC-7 |

## 분기·예외
| 상황 | 기대 동작 |
|---|---|
| 모집중이 0건 | 빈 상태 안내 + 전체 탭 유도 |
| 마감일이 지난 스터디에 직접 URL 진입 | 마감 안내, 신청 버튼 비활성 |
| 비로그인 상태로 신청 시도 | 로그인 유도 후 원래 위치로 복귀 |

## 커버리지
이 시나리오가 다루는 Story: ST-003 · ST-007 · ST-012
다루지 않는 Story: (있으면 명시)
```

## 3. 작성 원칙

1. **검증 포인트를 AC 에 연결한다.** 연결할 AC 가 없으면 Story PRD 에 AC 가 빠진 것 — 그쪽을 먼저 채운다
2. **예외를 주 흐름만큼 쓴다.** 웹에서 실제 문제는 대부분 분기에서 생긴다
3. **화면 이름이 아니라 사용자 행동으로 쓴다.** "목록 화면"이 아니라 "스터디를 찾는다"
4. 새 요구가 필요해 보이면 **US 에 쓰지 말고** Story 를 먼저 등재한다 (Ingest 모드)

## 4. 커버리지 점검

전체 Story 중 어떤 시나리오에도 등장하지 않는 것이 있으면 목록으로 보고한다. 그 Story 는 실제 사용 맥락이 검증되지 않은 상태다.

## 5. 자가 검증 체크리스트

- [ ] 참조한 Story 가 전부 `stories.md` 에 실재하는가
- [ ] 각 단계 검증 포인트가 실재하는 AC 를 가리키는가
- [ ] 예외 분기가 최소 3개 이상인가 (없다면 정말 없는지 재확인)
- [ ] 비로그인·권한 없음·데이터 0건 세 가지를 다뤘는가
- [ ] 커버리지 미포함 Story 를 명시했는가
