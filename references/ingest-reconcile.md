# Ingest / Reconcile — 소스 투입 → Story 레지스트리 갱신

> 요구사항 소스를 받아 `SRC-####`로 적재하고, Story 를 추출·정규화·중복판정하여 `stories.md`에 반영한다. 외부 트래커 동기화 단계는 없다 — 레포 파일이 최종 상태.

## 1. 입력 유형 판정

| 유형 | 신호 | 초기 상태 |
|---|---|---|
| **회의록·논의 기록** | 대화체, 결정/액션 아이템 | `백로그` |
| **기능목록·요구 목록** (csv·엑셀·표) | 나열형 항목 | `백로그` |
| **프로토타입** (JSX/HTML/이미지) | 화면 코드 또는 캡처 5장+ | `기획대기` |
| **PUD (구동 중인 제품)** | 실제 코드베이스·URL | §2.2 매핑으로 추정 |
| **기타양식** (MRD·제안서) | 문서 | `백로그` |

- 사용자가 명시하지 않으면 에이전트가 1차 판정. 신호 명확하면 즉시 진행, 경계 모호면 **1회 확인**
- 유형 판정 결과는 `INDEX.md` 항목에 기록

### 2.2 PUD 구현 단계 매핑

코드베이스가 입력이면 **실제 파일을 읽어** 각 요구의 구현 정도를 판정하고 상태를 추정한다. 추측 금지.

| 코드 상태 | 추정 Story 상태 |
|---|---|
| 화면·API·저장 모두 동작 | `배포완료` |
| 화면·API 있으나 저장 미연결 | `개발중` |
| 화면만 존재(mock 데이터) | `기획완료` |
| 타입·주석에 흔적만(`TODO`) | `백로그` |
| 흔적 없음 | 신규 `백로그` |

- 판정 근거를 **파일 경로 + 줄 번호**로 남긴다 (`stories.md` 비고 또는 Story PRD)
- 상태를 올릴 때는 보수적으로. 근거가 약하면 한 단계 낮게 잡고 비고에 사유 기록

---

## 2. Step 1 — 소스 적재

1. 발번 대장에서 `SRC-####` 발급
2. 원본을 `research/_sources/SRC-####-<유형>-<YYYY-MM-DD>.<ext>` 로 **그대로** 저장 (가공·요약본으로 대체 금지)
3. `INDEX.md`에 등록: SRC · 유형 · 제목 · 투입일 · 요약 1줄 · **생성/갱신 Story 역참조**(나중에 채움)
4. 프로토타입이면 `features/{f-slug}/_source/SRC-####-prototype-<날짜>/` 에 폴더째 보관

> 소스는 **불변**. 같은 내용이 다시 들어와도 새 SRC 로 적재하고 중복 제거하지 않는다. 중복 판정은 Story 층에서만 수행.

---

## 3. Step 2 — Story 추출·정규화

### 3.1 정규문장 형식 (Hard Rule)

```
[Actor]로서, [무엇을] 할 수 있다.
```

- Actor 는 `_SHARED_CONVENTIONS.md §10` 표준명(또는 `_project.md` 치환명) **정확 일치**
- **금지**: ID 접두사(`ST-012 로그인…`), 요약·태스크명(`로그인 구현`), 구현 방법 직접 명시(`JWT 를 발급할 수 있다`)
- **사용자 가치**를 표현할 것. 시스템 내부 동작은 Function 으로 분리

정규식 검증: `^.+로서, .+할 수 있다\.$`

### 3.2 입도 기준

- **1 Story = 1 사용자 목표**. "그리고"로 두 목표가 붙으면 분리
- 화면 단위가 아니라 **목표 단위**. 한 목표가 3화면에 걸쳐도 1 Story
- 시스템 내부 처리(스케줄러·마이그레이션·연동)는 Story 가 아니라 **Function**

### 3.3 우선순위

| 등급 | 기준 |
|---|---|
| P0 | 서비스 성립 필수. 없으면 출시 불가 |
| P1 | 핵심 경험. 초기 릴리스 목표 |
| P2 | 개선·편의 |
| P3 | 후속·검토 |

- **출처 빈도가 높을수록 가중** (§7 소스 원칙)

## 4. Step 2.5 — Baseline Coverage Pass

`baseline-requirements.md`의 웹 기본 요건을 대조하여 **누락분을 Story 후보로 자동 보충**한다. 비적용 결정은 사용자 확인 후 P2 강등 또는 `폐기` 처리하고 `_HISTORY.md`에 사유 기록.

---

## 5. Step 3 — IA Coverage Pass

1. 추출된 Story 가 **어느 화면(IA 노드)에서 수행되는지** 매핑
2. 대응 노드가 없으면 `IA-###` 신규 발번 후 `ia.md` 트리에 추가
3. Story ↔ IA 는 **N:N** — 한 Story 가 여러 화면에 걸칠 수 있음
4. IA 노드에 Story 가 하나도 없으면 **고아 화면**으로 플래그 (설계 누락 신호)

---

## 6. Step 4 — 중복·유사 판정

| 판정 | 조건 | 처리 |
|---|---|---|
| **동일** | 같은 Actor + 같은 목표 | 기존 `ST-###`에 **출처만 추가**. 신규 발번 금지 |
| **유사** | 같은 목표, 조건·범위 다름 | 기존 Story 를 **더 정밀한 문장으로 갱신** 또는 하위 조건을 AC 로 흡수 |
| **신규** | 위에 해당 없음 | 신규 발번 |
| **상충** | 같은 목표인데 결론이 반대 | **1회 보고 후 사용자 결정** — 임의 병합 금지 |

### 6.1 상태 인지 분기

- 대상 Story 상태가 **`배포완료`** → in-place 수정 금지. **신규 `ST-###` 등록 + 선행 링크(승계)**. `_HISTORY.md` 변경유형 = `신규(승계)`
- 그 외 활성 상태(재오픈 포함) → in-place 업데이트

---

## 7. Step 5 — Epic·Feature 매핑

- **Epic**: 모든 Story 는 정확히 1개 Epic 소속 (Orphan Zero). 적절한 Epic 이 없으면 **변경 계획에 신규 Epic 신설을 포함**
- **Feature**: N:N. 같은 Story 가 여러 Feature 에 등장하면 Feature 컬럼에 slug 누적

### 5.0 Prototype Update Cascade

기존 프로토타입의 새 버전이 들어오면:

1. **영역 정본 확인** (`canonicals.md`) — 정본 있는 영역이면 "정본에 반영 vs Sub 분리" **1회 질문**
2. 새 SRC 로 적재 (옛 버전 삭제 금지)
3. 화면 차이(added/changed/removed)를 도출 → 영향 Story·IA 노드 식별
4. 영향 Story 의 AC·화면 스펙 갱신 → Feature PRD §4.5 반영
5. removed 화면에 붙어 있던 Story 는 **폐기 후보**로 플래그 (자동 폐기 금지 — 계획에 포함해 승인)

---

## 8. Step 6 — 레지스트리 반영

`stories.md` 행 구성:

| ID | 정규문장 | Actor | 모듈 | P | 상태 | Epic | Feature | IA | 출처 | 비고 |
|---|---|---|---|---|---|---|---|---|---|---|

- ID 는 **발번 대장에서 발급** (`_SHARED_CONVENTIONS.md §4.1`)
- 출처는 `SRC-####` 쉼표 누적 (append-only)
- `stories-index.md` 는 정규문장만 뽑은 자동 생성물 — 직접 편집 금지

---

## 9. Step 7 — 영향 문서 플래그 & 자동 체이닝

### 7.1 PRD/FS/US 자동 체이닝

Hard Gate(프로토타입 코드 또는 캡처 5장+)가 충족되면 **같은 라운드에서** 다음을 자율 진행한다. 새 승인 요구 금지 (§3.5 단일 승인에 이미 포함).

```
Ingest → Story PRD → 검증 루프 → PR
```

Hard Gate 미충족(회의록·기능목록만)이면 **PRD 착수하지 않고** Story 등재까지만 하고, 그 사실을 종결 보고에 명시.

### 7.2 영향 문서 플래그

변경된 Story 를 참조하는 Story PRD·Feature PRD 를 식별해 `_HISTORY.md` 영향 하위 컬럼에 `☐ 필요`로 기록. **본 세션에서 디스패치 가능한 것은 즉시 처리**하고 `☑ 완료`로 전환. "사유 기록"으로 ☐ 를 ☑ 로 둔갑시키지 않는다.
